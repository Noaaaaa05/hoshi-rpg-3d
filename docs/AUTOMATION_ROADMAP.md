# 完全自動開発に向けた改善の優先順位

`main` の `527c95a`（PR #18）を2026-11-17に調査した結果。目標は、iPhoneから日本語で依頼するだけで、制作・実装・テスト・公開までをAIが進められること。機能ごとの実装状況は [AUTOMATION_PROGRESS.md](AUTOMATION_PROGRESS.md) の表にある。ここには、自動化が止まる箇所と対応の順番をまとめる。

## 優先度1：自動化が止まっていた箇所（このPRで対応）

| 止まっていた箇所 | 対応 |
| --- | --- |
| クラウドのセッションにはPlaywrightの指定版に合うブラウザがなく、ブラウザテストを実行できなかった | `HOSHI_CHROMIUM_PATH` でインストール済みのChromiumを指定し、`npm run test:browser:chromium` で実行する。WebKitは `Game checks` で確認する |
| 形式は正しいが遊べないデータを検出できなかった（受注できないクエスト、入れない訪問先など） | `rpg:check` と `rpg:apply` に「遊べるか」の検査を追加した。該当する変更は保存前に止まる |
| GLBを登録するときのSHA-256、骨数、三角形やテクスチャの上限を手作業で調べていた | `npm run rpg:asset` が計測し、登録エントリを依頼JSONの形で出力する |
| 公開URLの確認が手作業で、セッションからは `github.io` に接続できなかった | `main` へのpushごとに `Pages verification` が公開URLと `main` をSHA-256で照合する。結果はActionsから読める |
| `claude/**` へのpushでは `Game checks` が動かず、PRを作るまでWebKitの結果が分からなかった | pushの対象に `claude/**` を追加した |
| 同じモジュールを別の `?v=` で読み込むと、ブラウザが二重に評価する（`combat.js` が該当していた） | `npm run check` が検出して止める。`storage.js` の指定をそろえた |

コマンドの使い方は [RPG_AUTOMATION.md](RPG_AUTOMATION.md) の「追加前後の検査」にある。

## 優先度2：所有者の判断と設定が必要

リポジトリの設定や公開の方針に関わるため、AIだけでは進めない。

1. **Claudeのブランチから追加データを自動公開する。** リリースゲートは `codex/rpg-content-*` のブランチだけを通す。Claude Codeのセッションは割り当てられた `claude/...` ブランチで作業するため、追加データだけのPRでも自動マージされない。対応は次のどちらか。
   - ゲートが通すブランチに `claude/` を加える。作成者、変更ファイルが1件、追加のみ、最新の `main`、全チェック合格という他の条件は変えない。
   - 依頼のたびに、`codex/rpg-content-<作業名>` へpushしてよいと伝える。コードの変更は要らない。
2. **コードを含むPRを自動でマージする。** `main` に保護ルールを設定し、`Game checks` の `game` を必須チェックにして、リポジトリのauto-mergeを有効にする。設定後は、所有者がPRを了承した時点でauto-mergeを予約でき、合格と同時にマージされる。
3. **有料のMeshyワークフローに承認者を付ける。** いまは実行者が所有者であることを確認している。Claude Codeのセッションは所有者の権限で動くので、この確認ではAIによる起動を区別できない。GitHubのEnvironmentに承認者を設定し、有料のジョブをそのEnvironmentで動かすと、実行のたびにGitHubアプリでの承認が必要になる。
4. **セッションから公開URLを開けるようにする（任意）。** Claude Codeの環境設定で `noaaaaa05.github.io` への接続を許可すると、セッションから公開URLを直接テストできる。
5. **開いたままのPRを整理する。** PR #19（Claude Code向けの引き継ぎ資料）とこのPRは、同じ行を変更していない。どちらを先にマージしてもよい。PR #8は古い `main` が基点で、前転はPR #16で反映済み。

## 優先度3：3Dモデルの生成パイプライン（有料、承認制）

見た目を3Dモデルへ置き換えるには、生成から登録までの経路が要る。いまあるのは主人公のモーション5種を生成する `Meshy motions`、既存タスクの無料取得、計画だけを作る `character-plan` と `world-plan`。

1. キャラクターと小物の生成を1本の経路にする。Text to 3D（またはImage to 3D）、リメッシュ、リギング、アニメーション、取得、`rpg:asset`、依頼JSON、PRの順。承認ID、上限、再送防止は `Meshy motions` の仕組みを使う。
2. 取得したGLBを上限（三角形15,000、テクスチャ2048px・4枚、5MiB）に収める処理をActionsで実行する。`scripts/optimize-hero.py` はBlenderが必要で、骨格のないモデルだけを扱う。
3. 使い終えたワークフローを整理する。`Meshy forward roll - ONE SHOT` は予約済みのタグで再実行できず、`Meshy forward roll status` は固定のタスク専用。どちらも `Meshy existing task (free)` で代替できる。

料金は実行の直前に確認し、対象・回数・上限を示して所有者の承認を待つ。

## 優先度4：ゲーム側の拡張（コードのPR）

1. **移動ボタンが出ない不具合。** `js/rpg-world.js` の `nearby()` は、3.2m以内に会話できるキャラクターがいると「話す」を優先する。仲間は主人公の約2.4m後ろを付いてくるので、仲間が近い間は移動先（`exit`）のあるエリアで「移動」が出ない。いまのカタログに `exit` はなく、まだ起きていない。`exit` を使う依頼の前に直す。
2. カタログで表現できない要素を増やす。仲間の戦闘、技専用のモーションと演出、敵の行動の種類（`slime` と `goblin` のみ）、クエストの目標（訪問と討伐のみ）、報酬（アイテム1種のみ）、店、独立した街やダンジョン。
3. 集落（`js/village.js`）のNPCと薬草店をカタログへ移す。会話のボタンとパネルがカタログ側と二重になっている。
4. `?debug=1` のときだけ使える移動の入口を追加し、カタログの全NPCと全エリアを巡回するブラウザテストを作る。いまは依頼ごとに専用のテストを書く。
5. 森の木や岩、集落の建物の位置をNodeから参照できるようにし、配置が埋まらないかを検査する。`js/world.js` は `document` を使うため、いまはNodeで地形を作れない。
6. `?v=` の手作業の更新をやめ、ビルド番号を1か所にまとめる。

## 自動化できない確認

iPhone実機での操作、発熱、描画速度は、所有者が公開URLで確認する。自動テストが確認するのはLinux上のChromiumとWebKitまで。
